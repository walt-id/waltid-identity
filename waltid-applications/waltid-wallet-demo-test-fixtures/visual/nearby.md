# Nearby review and outcome contract

Nearby sharing uses the wallet's grouped rows, credential thumbnails, disclosure values and trailing action groups. Request meaning, reader trust, required elements, prepared approval and legal actions remain owned by the existing SDK session. The UI does not reconstruct those decisions.

The Compose and native hosts separate engagement, review, reader details, prerequisites and outcomes into focused components. Stored credential parsing runs off the UI thread and discards stale results. Selection rows represent credential selection, without a misleading details-navigation chevron. Requested field labels and values use the same normalized metadata as credential details; absent data remains explicitly unavailable. Receipts and prepared summaries reuse those labels and thumbnail art, showing only the approved field set. Reader identity and trust labels come from the immutable SDK review.

Actions stay trailing, on one line when labels fit, and wrap for compact widths or accessibility text. Permission remediation retains its busy state. Receipt and recovery actions stay in a footer while content scrolls. A completed response is described as locally sent; it is not presented as proof that the reader verified or accepted it. Expired prepared sharing requires review and a fresh approval; Try again does not silently recreate consent.

The deterministic catalogue covers QR readiness, a blocked Bluetooth prerequisite, trusted reader review with retention, prepared-approval expiry and the sent receipt. The compact review is 320×568 with Compose font scale 1.5 / SwiftUI accessibilityMedium; the second viewport shows the field value and retention notice above the pinned actions. The same synthetic request facts are read from `wallet-visual-data.json`. Native tests also decode the QR from the actual wallet chrome at two phone sizes. Semantic and lifecycle suites separately exercise credential/field choices, trust distinctions, permission/settings handling, stale decisions, cancellation, reconnect and prepared approval.

These fixtures do not request OS permissions or transmit credentials over BLE/NFC. Platform provider windows, hardware key prompts, physical-reader interoperability and background radio behavior need their separate live/device lanes. The catalogue records rendered states, not formal conformance.
