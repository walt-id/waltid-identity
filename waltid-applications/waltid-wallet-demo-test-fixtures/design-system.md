# Wallet demo UI conventions

These rules apply to Compose Android/iOS/Web, the native SwiftUI demo, and wallet-owned provider content. The SDK owns issuance, selection, consent, trust and signing policy. A view renders that state; changing its host must not create a new operation.

## Components and hierarchy

- Use the existing branding/theme injection and system text sizes. Group related facts using `WalletSection`, navigation rows and label/value rows, following Settings. Separate actionable rows from facts.
- Use `WalletActions` for decisions and `WalletActionBar`/`ReviewScaffold` for persistent review actions. Keep one primary action trailing in reading order, with secondary actions before it. Keep actions on one line when they fit; wrap or stack when text needs space. Never shrink or truncate a consent label to force a row.
- Use rounded buttons with intrinsic widths. Preserve 48 dp Compose and 44 pt Apple touch targets. Copy steppers have smaller visible capsules and separate accessible increase/decrease actions, values and limits.
- Labeled decisions use text: the primary has the accent fill, secondary actions use quiet text, and destructive confirmations use the error color. Declining or rejecting a request is an ordinary consent choice, not a destructive data operation. Do not require color or a pictogram to understand an action.
- Use `WalletSymbol` for Compose icons and platform symbols in SwiftUI. Decorative icons have no duplicate announcement; standalone controls need a meaningful accessible name. Keep child identifiers on children, since a SwiftUI container identifier can replace them.
- Use the same credential identity and typed values in every context. Compact thumbnails favor the supplied background color with a centered credential logo and ignore credential artwork. Without a usable background color, use available credential artwork; otherwise use the logo on the default background. Missing or failed artwork falls back to the logo/default background. Do not invent a credential logo. The title sits alongside, never inside a thumbnail. A single offered configuration uses full credential art, regardless of copy count. Multiple offers and sharing use compact rows. Follow the [credential-information contract](credential-information.md) for metadata, disclosure scope and unavailable values.
- Offer rows move their Receive switch below the identity when the title needs more horizontal space. Retain copy counts during resizing and preserve separate selection/information actions.
- Make compact reviews answer who, what information and what action. Keep required payment fields in their authoritative positions. Technical details are reachable but do not displace human-readable information.

## Screen chrome, feedback and motion

Each active destination has one header owner. Compose uses `WalletScreenHeader`; native screens use their navigation title/toolbar. Content owns section labels and credential identity. Information pages push within their current task sheet; independent consumers use the existing detail-sheet adapter. Back preserves the preceding page and selection. Sharing reviews keep selection and all disclosure values on the main screen, with inline list expansion and image viewing. Full credential browsing belongs to Home and issuance receipts; sharing has no separate credential Details route. Payment details and contextual requester/nearby accordions remain accessible. Nearby review uses the same choice and information-group components. Offered definitions do not invent issued values. Live review actions are hidden on detail pages. X closes the local task; protocol Reject is a separate explicit action and neither Back nor Close grants consent.

Use `MetadataDisclosure` for expandable fact groups. Its full row is a single named button with heading and expanded/collapsed semantics, a semibold body label and a rotating directional chevron. Keep 48 dp / 44 pt targets, wrapping labels and compact content spacing. Expansion state belongs to its page or request revision; a replacement payment request starts collapsed.

`WalletFooter` owns the control surface and padding. Consent footers contain actions, without routine “review…” messages or a second copy of a receipt. Relevant progress and errors belong in the scrollable content; field validation, trust warnings, transaction terms and consent stay beside their subject. An active nearby sheet owns its feedback. Local task dismissal uses a header X; protocol refusal uses a labeled secondary action. The native numeric editor has an accessible Done accessory; the action footer remains fully above the keyboard and accessory. Text fields use their keyboard submit key.

Compose `ReviewScaffold` measures header and footer before the body. Its content scrolls behind the material with measured end clearance; focus scrolling reserves the footer, and the footer intercepts taps within its surface. Native hosts use a single `safeAreaInset` for the footer. The footer background extends through the bottom safe area; the sheet host handles only top/horizontal insets, and pages without a footer handle their own bottom inset. Parent-consumed insets are not added again. The final item must scroll fully clear of wrapped actions and the keyboard; do not substitute a fixed bottom spacer.

| Renderer | Footer treatment and accessibility fallback |
|---|---|
| Compose Android | API 30–32 uses a translucent scrim without the RenderNode blur pipeline. API 33+ uses Haze core + blur in its default Balanced mode, one screen-owned source, 24 dp uniform blur and 42% background tint. Increased contrast or unavailable rendering uses the opaque background. No experimental window-backdrop or optical-refraction API. |
| Compose iOS / Wasm | The same bounded Haze blur/tint; available reduced-transparency and contrast preferences use the opaque background. Clear unavailable sources rather than retaining credential pixels. |
| Native SwiftUI | Thin system material through the home-indicator area; Reduce Transparency or increased contrast uses the opaque grouped background. Native navigation owns presentation/back transitions. |

Use existing navigation/animation APIs. A new hierarchical Compose page moves from the edge while its parent moves a quarter-width behind it; Back reverses the movement and layering, with RTL direction respected. Page and card movement use the native demo's spring settings (0.38 second response, 0.92 damping), preserving velocity when interrupted. The shared Compose `WalletMotion` supplies the Material motion scheme as well as page/card transitions. Sheet entry and exit use the same spatial spring, with Material still owning dragging, Back and dismissal. Disclosures use the same 180 ms ease-in-out as SwiftUI; local feedback uses 160 ms ease-out. Native review pages and sheets retain system navigation and presentation gestures, and PIN/signing pages share a restrained spring. Card/detail transitions follow selected identity, without delayed callbacks. Disclosure height and chevron animate together. Reduce Motion removes positional movement, including sheets and Material controls; removed/hidden cards cannot remain accessible or actionable. Activity decorates the native toolbar's stable symbol and geometry rather than replacing its label, and label changes do not inherit page animation. Animations never submit, retry or authorize a wallet operation. Test rapid reversal, interruption and disposal, and inspect short real-renderer clips separately from settled screenshots.

## Navigation and state

Wallet home exposes icon controls for Share nearby, Scan QR code and Settings, each with its accessible name. Scan opens a raised embedded-scanner sheet with bottom breathing room, reversible manual mode and field-adjacent Paste. Android offers its system camera action only when resolvable; iOS uses the embedded camera scanner. The scanner resolves supported links automatically; users do not choose a protocol. Unknown content remains editable. Resolving a link never submits consent. A FIDO hybrid code receives an honest platform-camera instruction.

Scanning retains a stable preview-sized progress surface until handoff. Receiving/sharing then shows preparation, review, recovery or a result for that request; it never reveals a URL-entry page while loading or after failure. Manual input belongs exclusively to the Home scanner sheet, and nearby sharing has its own Home action. Retry prepares the retained request only when possible; Close returns to Home. Failed transmission is never retried automatically.

Wallet-owned credential tasks use one sheet over Home, whether entered by Scan, an external link, nearby sharing or pending issuance recovery. Scanner resolution advances within the same sheet. Authentication and signing-key setup stay at the app root; requests wait until both are ready. Pin actions outside the content scroll area. Preserve selection and transaction-code edits during detail navigation and host recreation. Busy operations prevent duplicate submission. A new incoming link cannot replace an operation already consuming an offer or submitting consent. See [external flows](visual/external-flows.md).

PIN onboarding uses separate Choose and Confirm screens, with four underline positions and masked dots backed by one secure input. A matching confirmation opens the available OS biometric prompt. Cancellation or failure preserves an explicit Try again / Use PIN only choice; dismissal is not refusal. Pending setup survives restart and requires PIN verification before resuming. Follow the [PIN interaction contract](pin-onboarding.md). Signing-key setup starts with supported defaults and one Create/Restore confirmation; rows open focused customization. A failed creation's message/retry belongs to the unchanged summary configuration, not unrelated option pages. Settings reuses the same summary, with immutable properties read-only and reset consequences explicit. App unlock never substitutes for signing approval.

Nearby sharing is a task sheet over Home. Prepare sharing is off by default and only changes review timing; it never grants consent. Connection options opens that specific settings destination and returns to the same task. Close requests a legal SDK cancellation once; unavailable cancellation stays visible, and rejected cancellation restores the task with its error. During cleanup, retain the current page and its height, block further input, and indicate progress in the header. Native sheet visibility is independent of the SDK's active flag: an outside dismissal hides the sheet immediately and cannot reopen it while cleanup is pending. Keep Home behind the sheet until its exit animation finishes; do not replace the page with a taller closing scaffold or pop Connection options while closing. Done returns to Home or the external origin, with no accidental online-input page.

Sheet Close sits at the trailing edge of the header; navigation Back stays at the leading edge. NFC/QR connection choices form the primary group, separated from the Prepare sharing and Connection options group by extra space. Native switches retain their intrinsic size. The native entry menu is measured before opening its sheet, with space for native toolbar/drag-handle chrome; overflowing or unmeasured content uses the full-height sheet with scrolling. Capture that entry height before starting the session, then present its first usable state: connection choices, an actionable prerequisite, or an error. While starting, the Home nearby control shows progress and can cancel. Transient prerequisite checks and preparation never replace each other during the entrance animation. Keep detent identities fixed during the presentation. Sheet sizing never subtracts a changing scroll viewport or starts full-height just to shrink after opening. The Compose chooser wraps its content within the available sheet height. Keyboard-led input and QR engagement use the full-height presentation. Empty action footers are omitted. Native nearby content and navigation persist through dismissal; reset them only after both the sheet's dismissal callback and SDK cleanup finish.

Use the same sheet host for context QR scanning, independent credential/technical information, trust import and nearby approved-data summaries. Long information scrolls; it does not become an alert or a centered card dialog. The full-screen image viewer and platform confirmation dialogs/pickers retain their distinct roles. Information pages inside a task keep both a leading Back action and its trailing, correctly enabled Close action. Trust import uses the shared bottom primary action and a header Close. Pending external requests offer Close at the app root during unlock/setup, with the same busy guard as the active review. Closing an ordinary request stays in the wallet. Android Credential Manager activities and Apple provider extensions retain their system-owned contexts and result handling. Closing the scanner cancels its owned resolution work; late callbacks cannot reopen a dismissed task. Approved-data sheets close when their prepared approval is replaced or removed.

Fully completed receive/share success returns after five idle foreground seconds. Touching or scrolling the result keeps it open; a screen reader disables automatic dismissal, and Android's recommended accessibility timeout can extend it. Backgrounding cancels the timer, and a replaced operation cannot close its successor. Partial, pending, uncertain, declined and error outcomes require an explicit action. Keep Done reachable. OS-owned provider results follow their caller's completion contract.

## Structure and evidence workflow

Prefer one public rendering entry per file, with small private helpers beside it. Split orchestration, reusable content and platform hosting when they have different responsibilities. Extract stable concepts, not identical-looking fragments with different semantics. Reuse the Kotlin shared UI and the existing shared Swift package instead of adding a new public SDK UI layer.

For each changed route:

1. Check this contract and the [payment](visual/payment-consent.md), [nearby](visual/nearby.md) or credential contract that governs it.
2. Choose existing shared synthetic fixture data; add a distinct state only when it exposes a different risk. Use the same renderable content for previews and tests, without starting services.
3. Add semantic assertions and the applicable renderer cells to the [catalogue](visual/catalogue.json). Cover compact width, large text, dark mode or RTL where the change affects layout. Use real host tests for keyboard, lifecycle and system UI.
4. Deliberately record, inspect, then run [the comparison runner](visual/README.md) with recording disabled. A record-mode run is not a pass. Never accept new baselines automatically in CI.
5. Keep local screenshots, hosted checks, live issuer/verifier interactions and physical-device proof separate. A component image cannot prove a system picker, biometric prompt, BLE/NFC exchange or TS-12 compliance.

The selected patterns adapt grouped Settings rows, digital-wallet disclosure/detail hierarchy and compact payment-sheet actions. Borrow hierarchy and interaction ideas while preserving the wallet's metadata and consent contract; do not copy third-party branding, assets or unrelated behavior.

The repository runner and these contracts are the canonical workflow. Existing KMP validation, Apple tooling and mobile capture skills remain sufficient; a separate installed wallet skill should link here rather than duplicate commands or policy. Global skill installation is not required to maintain these screens.
